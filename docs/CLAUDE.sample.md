# Sample target-repo CLAUDE.md

Copy the body below the horizontal rule into the **root `CLAUDE.md` of the repo you
run build-fleet against** (not this repo — `/Users/.../build-fleet/CLAUDE.md` is
contributor instructions for the plugin itself). Fill in the `<...>` placeholders,
delete this preamble.

**Why a build-fleet-aware CLAUDE.md matters.** CLAUDE.md outranks skills in
instruction precedence, but the gate hooks enforce the protocol regardless. A generic
"write your plan to `tasks/todo.md`" or "just fix the bug" directive therefore does not
win — it produces an agent that confidently attempts a blocked action, eats an exit-2,
and burns a cycle. The file is also injected into **every dispatched role agent**, so a
line addressed to the orchestrator ("use subagents liberally") is read by the coder too.

The most common conflicts in a hand-written CLAUDE.md, and what actually happens:

| Generic rule | Under build-fleet |
|---|---|
| "Write the plan to `tasks/todo.md`" | Blocked — `block-source-before-finalized` rejects non-`.sdd/`, non-`tests/` writes until FINALIZED; `restrict-reviewer-writes` confines writes to `.sdd/<active>/` during REVIEW and CHANGE_REVIEW. The instruction fires exactly when the gate is closed. |
| "Given a bug, just fix it" | Blocked — `require-reproducing-test` holds source until a reproducing test exists, even for sev0. |
| "Use subagents liberally" | Reaches the coder and qa, whose tool allowlists and write lanes are deliberately tight. |
| "Plan mode for anything non-trivial" | Duplicates the planning surface — `spec.md` (feature) and plan-review (product) already carry human gates. |
| "Never mark complete without proving it" | Survives, but is already mechanized: the counterfactual gate, acceptance↔test mapping, `stop-tests`. State it in that vocabulary rather than as self-review. |

The marker pair near the top of the sample is deliberate: it reserves the
product-memory region so `/build-fleet:plan-finalize ratify` splices in place there
rather than appending at EOF. Keep both marker lines together or delete both — a BEGIN
without an exact END line makes `scripts/product-memory-splice.sh` refuse to write.

## Project facts

- **Stack:** `<language, framework, package manager, runtime version>` — or leave this
  to `/build-fleet:new-product`, which infers the real stack from an existing codebase
  into `.sdd/_product/STACK.md` as the binding stack-of-record.
- **Test command:** `<test command here>`
- **Lint / typecheck:** `<command here>`
- **Conventions:** `<naming, module layout, error handling, logging — the things a
  reviewer would cite as a [major]>`

Name the test command explicitly. The `stop-tests` hook silently no-ops on an
unrecognized stack, so an unnamed test command quietly disables a gate — and
`/build-fleet:handoff` refuses on missing or failing tests, which is a worse place to
discover it.

## How work enters this repo

| Kind of work | Entry point |
|---|---|
| A feature | `/build-fleet:new-feature <slug> "<description>"` |
| A bug with unknown cause | `/build-fleet:triage` |
| A PRD or multi-phase plan | `/build-fleet:new-product <slug>` → `/build-fleet:plan-review` → `/build-fleet:plan-finalize ratify` |
| A chore touching no source | Do it directly, and only while `.sdd/ACTIVE` is empty |

`/build-fleet:status` reports where things stand. The `sdd-protocol` skill is the
authority on the workflow; where this file and that skill disagree, the skill wins —
the hooks enforce it either way.

## Working inside the loop

- **`.sdd/<item>/` is the plan and the shared memory.** `spec.md` + `acceptance.md`
  are the contract, `PROGRESS.md` is the state, `IMPL_NOTES.md` and `DECISIONS.md`
  hold deviations and rationale. Keep no parallel plan file — writes outside `.sdd/`
  are gate-blocked before FINALIZE anyway.
- **One item in flight.** Don't open a second feature; `/build-fleet:park <reason>` is
  the sanctioned way to preempt the active one.
- **Never hand-edit a `STATUS:` or `PHASE:` line to advance the machine.** Move state
  through the gates: `/build-fleet:finalize`, `/build-fleet:handoff`,
  `/build-fleet:resolve-escalation`.
- **Escalation is a designed outcome, not a failure.** On `PHASE: ESCALATED`, stop and
  surface the conflict — do not route around it. A human runs
  `/build-fleet:resolve-escalation <decision>`.
- **Commit `.sdd/`** — it is the audit trail. The scaffolded `.sdd/.gitignore` already
  excludes the per-worktree locks. Work on a feature branch.
- **Run fleet commands outside plan mode.** Plan mode is for work outside the loop.

## If you are a dispatched role agent

Stay in your lane. Reviewers (architect, qa) write only inside `.sdd/<active>/` and
never source. The coder writes source only while `PHASE: BUILD`, and only once qa's
failing tests exist. Devops writes CI/release artifacts only after CHANGE_REVIEW
approval. Use subagents for research and exploration only — anything that **writes**
goes through a fleet role. Load any skills routed to you in `SKILL_MANIFEST.md`.

## Standards

- **Root cause, not workaround.** A departure from the spec is a `deviation:` line in
  `IMPL_NOTES.md`, not a silent choice.
- **The simplest change that satisfies the spec.** Worth one deliberate pause on
  non-trivial work; skip the ceremony on obvious fixes.
- **Done means proven.** Every acceptance criterion names the test that exercises it,
  and each test must fail if the change is reverted (the counterfactual gate). Don't
  pre-empt CHANGE_REVIEW with self-review — let the adversarial pass run.
- **Corrections become durable.** Record a repeated mistake as a pattern only while
  `.sdd/ACTIVE` is empty (mid-item, that write is gate-blocked); if it is an
  architectural call, it belongs in `DECISIONS.md` as an ADR. Better still: if a rule
  matters, make it a hook or a test, not a bullet.
