# build-fleet lite — design

**Date:** 2026-10-15
**Status:** draft for review (design approved section by section in brainstorming on
2026-10-14); implementation plan follows approval
**Ships as:** part A of build-fleet v0.12.0 ("lite"). Parts C (drift gate), D (lean
descriptions and bodies) and B (four files per feature) each get their own spec and
ship in the same release.
**Supersedes:** the user-facing command surface. Every gate, hook, agent and workflow
stays; only who may invoke which command changes.
**Revised:** 2026-10-15 after an independent Gemini review (§8).
**Evidence:** roadmap review, step 1 (https://claude.ai/artifact/RjjQEmAJ6woyP1aGQXdK4j);
Claude Code command frontmatter as documented on code.claude.com (researched
2026-10-14).

## 1. Problem

A new user meets 23 slash commands, five of them for a single feature's happy path
(`new-feature`, `review`, `revise`, `finalize`, `build`, `handoff`), each with its own
flags, refusals and "next command" hints. The roadmap review found that this surface,
more than the gates, is what a newcomer can't get past. The gates are the product; the
command list is plumbing that leaked out.

The goal is to keep it simple. The end state is a plugin where a user knows five
commands and nothing else. Hiding the other commands is the first step; deleting them
as the lite commands absorb their logic is the end goal.

## 2. Decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | **Five user commands:** `start`, `build`, `ship`, `fix`, `status`. | One per thing a person wants to do. |
| D2 | **Every other command gets `user-invocable: false`.** Hidden from the `/` menu and untypeable, still runnable by Claude. | Claude Code has no per-command opt-in, alias or profile mechanism; this is the only switch. Two plugins in one marketplace would double-run hooks and break `CLAUDE_PLUGIN_ROOT` paths. |
| D3 | **Lite commands are thin drivers** over `scripts/lite-next.sh`, which reads `.sdd/` state and names the next step. The driver runs that step through the Skill tool, reads its signal line and asks again. | One routing table, testable in bash; no prompt text duplicated. Rejected: merged prompts (duplication, very long prompts), a workflow-JS driver (runs agents, not commands, and can't stop for a human). |
| D4 | **Human decisions live in `status`.** `status` takes `park <reason>`, `resolve <decision>` and `ratify [force]`. `park`, `resolve-escalation` and `plan-finalize` are deleted. | Keeps the count at five: Claude can't park, resolve or ratify on its own. |
| D5 | **Checkpoints:** `start` stops when the spec is ready; running `build` is the approval; `ship` stops at devops' explicit OK. | Matches where a person actually wants to look. |
| D5a | **`build`, `ship` and `status` are human-only** (`disable-model-invocation: true`). `start` and `fix` stay runnable by Claude. | Makes D5 enforced, not promised: Claude can't approve its own spec, ship, or take a human decision. Cost: Claude can't run these three for the user. |
| D6 | **Product tier folds into `start`.** `start` with no idea takes the next unblocked backlog feature; `start --product "<vision>"` scaffolds and reviews the product plan and stops for `status ratify`. Product memory regenerates automatically. | No separate product commands to learn. |
| D7 | **Renames to free the names:** the bug-lane step `fix` becomes `apply-fix`; the BUILD step `build` becomes `implement`. | The lite names must be unique. |
| D8 | **Re-running a lite command resumes.** No command takes a "continue" flag. | State is in `.sdd/`; the script reads it. |
| D9 | **Roster, budget and shape flags leave the user surface.** Durable defaults stay in `PROGRESS.md` (`REVIEW_SHAPE`, `CYCLE_BUDGET`, `BUILD_CYCLE_BUDGET`). | Anyone who needs them sets the field or asks Claude to run the hidden command. |

## 3. Design

### 3.1 The surface

| Command | Does | Stops at |
|---|---|---|
| `/build-fleet:start [idea \| --product "<vision>"]` | Scaffolds a feature (or takes the next backlog feature), asks the clarifying questions, drafts the spec, reviews and revises it until clean or escalated. With `--product`, scaffolds and reviews the product plan. | Spec ready; plan ready for ratification; another item in flight; escalation. |
| `/build-fleet:build` | Finalizes the spec, then runs the tests-first build (standard or parallel, per the classifier's `BUILD_MODE`). | Build done; escalation; a refusal. |
| `/build-fleet:ship` | Runs change review, the coder fix loop, and hands off to devops. | Devops' OK or refusal; escalation. |
| `/build-fleet:fix <symptom>` | Runs the whole bug lane: triage, reproduce, hypothesis, diagnose, apply-fix, verify, ship-fix. | Devops' OK; escalation; a refused diagnosis that needs a human. |
| `/build-fleet:status [park <reason> \| resolve <decision> \| ratify [force]]` | Bare: reports state and the next command (read-only). With a decision: applies it. | — |

Every lite run ends with exactly one line:

```
BUILD_FLEET_LITE_DONE: {"stop":"<reason>","next":"/build-fleet:<cmd>"}
```

`next` is omitted when nothing follows (e.g. after a ship). Stop reasons:
`spec-ready`, `plan-ready`, `built`, `shipped`, `item-in-flight`, `parked`, `escalated`,
`step-refused`, `no-progress`, `step-cap`, `unknown-state`, `nothing-to-do`.

`start` with a different item in flight does not park it. It stops `item-in-flight`
and points to `/build-fleet:status park <reason>`.

### 3.2 Hidden commands

After the change, `commands/` holds 24 files: the 5 lite commands and 19 hidden steps.

- **Hidden (19):** `new-feature`, `review`, `revise`, `finalize`, `implement` (was
  `build`), `deep-build`, `handoff`, `triage`, `reproduce`, `diagnose`, `apply-fix`
  (was `fix`), `verify`, `ship-fix`, `new-product`, `plan-review`, `next-feature`,
  `product-memory`, `dispatch`, `scaffold-workflow`.
- **Deleted (3):** `park`, `resolve-escalation`, `plan-finalize`. Their bodies move into
  `status`, unchanged in behavior.

A hidden command keeps its own `allowed-tools`, signal lines and refusals. Its "next
command" hints become internal: the driver does not relay them; it relays only its own
`BUILD_FLEET_LITE_DONE` line. Hidden commands that a person still wants, such as
`scaffold-workflow` or `dispatch`, stay reachable by asking Claude for them in plain
words, since only typing is blocked.

### 3.3 `scripts/lite-next.sh`

```
lite-next.sh <start|build|ship|fix|status> [args…]
```

It reads `.sdd/ACTIVE`, the active item's `PROGRESS.md`, the spec's `STATUS`,
`finalize-gate.sh --report`, `ESCALATION.md`, and `.sdd/_product/`. It writes nothing.
It prints one line, either a step:

```
BUILD_FLEET_LITE_NEXT: {"step":"<hidden command or action>","args":"<string>","why":"<short>"}
```

or a stop:

```
BUILD_FLEET_LITE_NEXT: {"stop":"<reason>","next":"/build-fleet:<cmd>","why":"<short>"}
```

`"step":"action:hypothesis"` names an orchestrator action that has no command: write
the root-cause hypothesis into `diagnosis.md`. The driver carries it out itself.

Routing table (first matching row wins; rows for every command start with the
escalation and foreign-item checks):

| Command | State | Result |
|---|---|---|
| any but `status` | active item has `ESCALATION.md` or `PHASE: ESCALATED` | stop `escalated` → `status resolve <decision>` |
| `start`, `fix`, `build`, `ship` | the active item is on the other lane (a bug for `start`/`build`/`ship`, a feature for `fix`), or `start <idea>` / `fix <symptom>` arrives while any item is active | stop `item-in-flight` → `status park <reason>` |
| `start <idea>` | nothing active | step `new-feature` (it runs the classifier) |
| `start` | nothing active; a product plan exists and has not been reviewed | step `plan-review` |
| `start` | nothing active; product plan reviewed, not ratified | stop `plan-ready` → `status ratify` |
| `start` | nothing active; backlog has an unblocked feature | step `new-feature <slug>`, the slug read from `next-feature.sh` by the script itself |
| `start` | nothing active; no backlog and no idea | stop `nothing-to-do` |
| `start --product "<vision>"` | nothing active, no product tier | step `new-product` (the next run's "not reviewed" row picks up `plan-review`) |
| `start` | spec `DRAFT`, `TIER: trivial`, `CYCLE: 0` | stop `spec-ready` → `build` (finalize's trivial fast path skips review) |
| `start` | spec `DRAFT`, no review this cycle | step `review` |
| `start` | report has open items, `spec_changed: false`, cycles left | step `revise` |
| `start` | report has open items, `spec_changed: true`, cycles left | step `review` |
| `start` | finalize report ready | stop `spec-ready` → `build` |
| `build` | spec not ready | stop → `start` |
| `build` | spec ready, not `FINALIZED` | step `finalize` |
| `build` | `FINALIZED`, `BUILD_STATE` absent | step `implement` |
| `build` | `BUILD_STATE: started` or `needs-iteration` | step `deep-build` (it requires the existing failing suite and is resumable) |
| `build` | `BUILD_STATE: done` | stop `built` → `ship` |
| `ship` | nothing active | stop `nothing-to-do` |
| `ship` | `BUILD_STATE: done`, or `BUILD_STATE` absent with `PHASE: CHANGE_REVIEW` or `HANDOFF`; phase `BUILD`, `CHANGE_REVIEW` or `HANDOFF` | step `handoff` |
| `ship` | otherwise | stop → `build` |
| `fix <symptom>` | nothing active | step `triage` |
| `start`, `fix` | `PHASE: PARKED` on the active item | stop `parked` (resuming a parked item stays a deliberate human edit, as today) |
| `fix` | bug lane at `REPORT`/`REPRODUCE` | step `reproduce` |
| `fix` | `DIAGNOSE`, no hypothesis in `diagnosis.md` (or the last one refuted) | step `action:hypothesis` |
| `fix` | `DIAGNOSE`, hypothesis present | step `diagnose` |
| `fix` | `FIX` | step `apply-fix` |
| `fix` | `VERIFY` | step `verify` |
| `fix` | `HANDOFF` | step `ship-fix` |
| `fix` | nothing active, no symptom | stop `nothing-to-do` |
| `status` | — | stop with the `next` that the matching row above would give |
| any | state not covered above | stop `unknown-state` |

**Spec ready** means `finalize-gate.sh --report` says ready, or the trivial fast-path
condition holds (`TIER: trivial`, `PHASE: SPEC`, `CYCLE: 0`).

**`BUILD_STATE`** is a new `PROGRESS.md` field: `implement` writes `started` before it
dispatches qa and `done` when it emits `BUILD_FLEET_BUILD_COMPLETE`; `deep-build.js`'s
scribe writes `needs-iteration` or `done` through its `state_delta`. An interrupted
build is left at `started`, which routes to `deep-build` rather than back to
`implement` (whose re-run guard would refuse `build-already-started`). Today nothing durable says a build finished, so the
script could not route `build` and `ship` without it. A feature already past BUILD when
the release lands has no field; `ship` then treats `PHASE: CHANGE_REVIEW` or `HANDOFF`
as built.

Each step names exactly one hidden command or action; a "then" never appears in a row.
The exact `.sdd/` fields each row reads (for example, how a refuted hypothesis is
marked in `diagnosis.md`, or how an unreviewed product plan is recognised) are pinned in the plan's first `lite-next.sh` task against the
current command bodies; where a field is missing, the plan adds it the way
`BUILD_STATE` is added here.

### 3.4 The driver loop

Each of `start`, `build`, `ship` and `fix` (body target: under 400 words) runs this
loop. `status` is not a driver: see §3.5.

1. Run `lite-next.sh <command> $ARGUMENTS` on the first pass, and `lite-next.sh
   <command>` with no arguments on every later pass. The idea or symptom is consumed by
   the step that scaffolds the item; passing it again would match the `item-in-flight`
   row against the item just created.
2. On a stop: print a short summary and the `BUILD_FLEET_LITE_DONE` line. End.
3. On a step: run the hidden command through the Skill tool (or carry out the action),
   wait for it to finish (a workflow step launches in the background; the driver waits
   for the workflow's result before asking again), and read its signal lines.
4. If the step printed any `*_REFUSE`, `*_FAIL` or `*_REFUSED` line: relay it verbatim
   and end with `{"stop":"step-refused","step":"<name>"}`.
5. If the step printed `BUILD_FLEET_DEVOPS_OK`: end with `{"stop":"shipped"}`. (Devops'
   OK closes the item, so the script would otherwise see nothing active.)
6. Go to 1.

**Guards.** The same step returned twice with no change to `PROGRESS.md` or the spec
stops `no-progress`. A hard cap of 12 steps per run stops `step-cap`. An unknown state
stops; the driver never guesses. This matches how the hooks fail closed.

The driver adds no state writes of its own, with one exception: `action:hypothesis`,
which writes the `## Root-cause hypothesis`, `## Blast radius` and `## Fix strategy` sections of
`.sdd/<slug>/diagnosis.md` (the orchestrator writes them today too). `fix`'s
`allowed-tools` carries `Write`/`Edit` for that; the existing `.sdd/` write hooks still
apply. Every other write happens inside a hidden command, under that command's
`allowed-tools` and the existing hooks.

### 3.5 `status`

`status` does not run the driver loop. It calls `lite-next.sh status` once, for the
`next` line only.

- **Bare:** today's report, plus the `next` line. When a product plan awaits
  ratification, the report includes what bare `plan-finalize` shows today (the plan and
  its open blockers). Writes nothing.
- **`park <reason>`, `resolve <decision>`:** the bodies of `park` and
  `resolve-escalation`, moved in, keeping their signal lines (`BUILD_FLEET_PARKED`, …).
- **`ratify [force]`:** today's `plan-finalize ratify [force]`. It ratifies; there is no
  separate dry-run token, because bare `status` is the dry run.
- Frontmatter: `disable-model-invocation: true`; `allowed-tools` is the union of the four
  commands' lists; the `model: haiku` pin is dropped because the decision forms need the
  default model.

### 3.6 Contract and docs

- **`docs/v0.2/CONTRACT.md`** is rewritten around the five commands and the
  `BUILD_FLEET_LITE_NEXT` / `BUILD_FLEET_LITE_DONE` lines. Headless callers that typed a
  hidden command (`claude -p "/build-fleet:review"`) break; this is called out in the
  CHANGELOG. The Hermes adapter polls `status-snapshot.sh` and is unaffected.
- **README** first screen: install, then a 60-second walkthrough of `start` → `build` →
  `ship`, then `fix` and `status`. Architecture, the hidden-step reference and history
  move to `docs/`.
- **`skills/sdd-protocol`** and its references, the agents and every command body that
  names a renamed or deleted command are updated. The pre-v0.12 names stay only in
  `docs/history/` and the CHANGELOG.
- **`CLAUDE.md`** layout block: 24 commands, 5 user-facing.

## 4. Failure handling

| Case | Behavior |
|---|---|
| A hidden step refuses or fails | Stop `step-refused`; the step's own line is relayed verbatim. |
| A workflow step returns `incomplete` or `scribe_apply: "failed"` | Treated as a failure: stop `step-refused`. |
| Same step, no state change | Stop `no-progress`. |
| 12 steps in one run | Stop `step-cap`; re-running resumes. |
| Unrecognised state, missing `jq`, unreadable `.sdd/` | `lite-next.sh` stops `unknown-state`; it never guesses. |
| Escalation at any point | Stop `escalated` → `status resolve <decision>`. |
| Skill tool can't run a hidden command (spike fails) | The design falls back to D3's rejected option 2: the lite bodies absorb the hidden prompts. The spec returns for review before that path is taken. |

## 5. Testing

1. **Go/no-go spike (first plan task).** In a scratch repo, confirm that a lite command
   can run a `user-invocable: false` command through the Skill tool, that the hidden
   command keeps its own `allowed-tools`, and that the driver can wait for a background
   workflow's result before continuing. The result is recorded in the plan ledger.
2. **`scripts/lite-next.test.sh`:** one hermetic fixture per routing-table row, plus the
   failure rows of §4, in the existing harness style. Written before `lite-next.sh`.
3. **Surface test** (`scripts/lite-surface.test.sh`): exactly five commands lack
   `user-invocable: false`; exactly `build`, `ship` and `status` carry
   `disable-model-invocation: true`;
   no file outside `docs/history/` and `CHANGELOG.md` references
   `/build-fleet:park`, `/build-fleet:resolve-escalation`, `/build-fleet:plan-finalize`,
   or the old step names `/build-fleet:fix` (as the bug step) and `/build-fleet:build`
   (as the BUILD step).
4. **Smoke test:** the existing bug-lane walk-through also asserts the step sequence
   `lite-next.sh fix` produces at each stage.
5. **Live run:** `start`, `build`, `ship`, `status` and `fix` on a scratch repo in
   `/tmp`, as the verified review's live run was done.

## 6. Release

- Ships as v0.12.0 with C, D and B. Each piece's plan lands on `release/0.12.0`; the
  release commit follows the atomic checklist (tag, `plugin.json`, `marketplace.json`,
  CHANGELOG, README counts, agent descriptions for any agent body that changed).
- CHANGELOG lists the breaking changes: hidden commands can't be typed; three commands
  deleted; `fix` and `build` renamed as steps; headless callers of hidden commands must
  move to the lite commands.

## 7. Out of scope

- Deleting the remaining hidden commands. That follows once the lite commands have run
  in real use.
- Lean descriptions and bodies (part D), the drift gate (part C), four files per feature
  (part B).
- The `finalize-gate.sh` gaps and the other deferred minors, which go into the v0.11.1
  patch before the measurement.

## 8. Review record

An independent Gemini 3.8 Flash (High) review of the first draft returned 15 findings;
10 were real and are fixed above:

1. D5's approval wasn't enforced → D5a makes `build` and `ship` human-only too.
2. `start <idea>` re-matched `item-in-flight` on its second pass → arguments go to the
   first pass only (§3.4).
3. `revise` would repeat → rows split on the report's `spec_changed` field.
4. An interrupted build re-routed to `implement` and was refused → `BUILD_STATE:
   started` routes to `deep-build`.
5. An unreviewed product plan had no row → added.
6. "Bare `ratify` stays a dry run" was ambiguous → `ratify` ratifies; bare `status` is
   the dry run.
7. `action:hypothesis` contradicted "the driver writes nothing" → stated as the one
   exception.
8. Rows with "X, then Y" didn't fit one-step output → one step per row.
9. `status` read as a driver → it isn't (§3.5).
10. Smaller: legacy features were stuck behind the "not done" row; `build`/`ship` lacked
    the lane check; parked items had no row.

Rejected: "the Skill tool can't run commands" (the spike tests this, and current Claude
Code merges commands into skills); "large features never reach deep-build" (`implement`
routes to deep-build itself on `BUILD_MODE: deep-build`); "a failed verify aborts the
bug lane" (verify reports a bounce as `BUILD_FLEET_VERIFY` `verdict: bounce`, not a
`*_FAIL` line).
